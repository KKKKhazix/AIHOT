# 正文与图片读取

正文读取位于抽取与编辑分析之间：`extract → read → analyze → publish`。它先确认正文范围，再按标题、相邻段落、图注和引用作者读取图片，保存 Markdown、逐图结果和原图快照。后续预筛、评分、结构抽取、摘要使用同一份文字证据，不再各自重新看图。页面和 Markdown 导出读取发布时固定的版本。

## 启用与配置

先应用数据库迁移 `0042_body_readings.sql`，更新 API、worker 和 web。默认关闭，不会在迁移或打开页面时调用模型。

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `BODY_READING_MODE` | `off` | `off` 保持原分析路径；`shadow` 仅处理显式指定的对照样本；`active` 将读取接入分析和发布 |
| `BODY_READING_MODEL` | `default` | 已注册的模型名称；可在后台“模型”中覆盖。必须支持视觉输入 |
| `BODY_READING_CONCURRENCY` | `1` | 每个 worker 同时读取的文章数，允许 1–8；多进程时并发相加 |

复用 `LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL` 等已有连接配置。默认模型需明确设置 `LLM_VISION=true`；名称带 vision 不代表接口已接收到图片。仍受 `MODEL_CALLS_ENABLED`、服务预算和付费回执控制。开发和自动化测试保持总安全阀关闭；测试使用本机 HTTP 桩，不调用外部模型。

`shadow` 不会自动读取全库，也不会改变文章、分析或发布指针。已经按 shadow 入队的任务，即使部署切换为 active，仍只保存对照结果。active 模式只让新入队的编辑类素材进入读取；已处理历史文章须显式重读。非编辑类信源不进入此流程。

## 信源规则

沿用信源 `config.body.selector` 和 `removeSelectors`，增加图片级规则：

```json
{
  "body": {
    "selector": ".article-content",
    "removeSelectors": [".share", ".recommend"],
    "images": {
      "keepSelectors": [".notice-table"],
      "removeSelectors": [".qrcode", ".ad-banner"]
    }
  }
}
```

示例选择器应按实际网页核对后配置。正文选择器缺失或命中多处时，网页抽取不会退回整页。只有确实通过该选择器抽取的快照才视为已确认边界；RSS/外部正文片段不会仅因来源有 selector 配置而跳过低质量候选的判断。图片可匹配自身或祖先元素，同一图同时匹配保留和排除会报错；人工指定保留的图不能被模型判为装饰图后丢弃。保留规则仍不能让模糊数字通过完整性检查。

没有可靠选择器且文本过短、抽取未确认或链接密集时，模型只能从已有内容块 ID 中选择正文。图片判断区分有效内容、装饰图片和无法读取；价格、单位、日期、脚注需一起转录，模糊项不得补写。

## 覆盖与失败处理

首版策略固定版本，不新增一批启发式环境变量：每篇最多 12 张图、32 个切片；每图最多 8 片，每批最多 4 张图或 8 片；原分辨率按 1600×1800 切片，相邻重叠 120 像素。单图下载上限 15 MiB、解码上限 4000 万像素，正文上限 500 个内容块、60000 字符。超限、多帧、格式不支持和模糊图会标记待核对，不会静默截断后宣称完整。内存用量与图像大小及并发相关，首次部署保持并发 1。

网络超时、429 和服务端错误使用原有退避重试；额度不足等待预算恢复；无法确认的识别结果留待核对。重试复用已完成图片和已支付回执，仅重新处理未完成图片。图片和切片在同一批内整体校验；一批响应截断或缺少图片结果时该批重新请求，不把半个表格当作成功。

付费结果未知会暂停，后台“运行”核对回执后可恢复；现有运维任务允许超过 30 分钟的未知回执自动放行一次，再次未知需要人工核对。对照任务恢复仍保持隔离。

新读取只有完整、素材修订和读取代数仍匹配时才能被接受；旧任务晚到只保留记录。分析也保存读取 ID。新正文和新分析一起发布；重读、人工修正或翻译尚未完成时，旧发布快照保持一致，不拼接不同版本。

## 后台与历史处理

后台内容详情增加“正文与图片读取”：查看逐图状态、保存的原图、转录 Markdown、失败原因及最近 5 个读取版本。支持重读、仅重试未完成图，以及基于同一素材修订人工修正/恢复旧正文。人工修正需要理由，追加版本和审计记录；保留的图片必须已保存快照。修正后仍需重新分析，才替换发布正文。shadow/off 不能应用人工修正。

下面是独立本地环境的后台示例，全部为虚构测试数据，没有调用外部模型：

![正文读取记录、保存图片与 Markdown 转录](assets/body-reading-admin.png)

小批历史处理脚本默认只列候选，不入队：

```bash
node --env-file=.env scripts/read-bodies.ts --id <article-id>
node --env-file=.env scripts/read-bodies.ts --source <source-id> --since 2026-09-28 --limit 20
```

核对候选后显式执行；同一批重试保持请求编号不变，避免重复增加版本和重复付费：

```bash
node --env-file=.env scripts/read-bodies.ts --id <article-id> --apply --request-id body-reading-batch-001
```

每批最多 50 篇，默认 20 篇。`--retry` 只重试未完成读取；默认跳过已人工修正的文章，`--include-manual` 才包含。脚本仅入队，实际模式、模型和总开关由 worker 决定，脚本与 worker 应使用一致配置。相同 URL 换图可通过显式重读重新验证 ETag/Last-Modified/内容字节；本迭代没有全站定时重新下载图片，避免无界请求和费用。

历史处理保留发布时间、发现时间，不发送旧文通知；超过 48 小时的修正更新已有事件摘要，不创建新的事件热度。来源全文和再分发权限仍有效，公开内容保持匿名可读；快照图片遵循当前发布可见性和来源全文许可，后台仍须管理员认证。

## 证据保存、部署与回退

图片原字节和展示快照保存在 `.data/body-assets/`（使用配置的数据目录），按内容 SHA-256 寻址；正文原始候选保存在数据库。API 与 worker 必须共享持久化数据卷。文件备份已包含 body-assets；现有 30 天派生缓存清理不删除这些证据。本版不自动删除读取历史和对应图片，需监控磁盘容量并在另行设计引用感知清理前保留。不要只恢复数据库而丢失图片目录。

建议先以 off 部署，再用 shadow 核对实际模型样本。验收应核对正文容器中的图片、标题中的执行日期与网页发布时间、数值单位和附注，并比较页面、Markdown、摘要和快照。离线 HTTP 桩只验证工程链路，不能证明模型识别准确率；未完成真实图片人工核验前不要切换全量 active。

暂停新读取可切回 off，已发布正文快照不会删除。需要更正内容时，在 active 下从已核实的旧版本创建修正，待重新分析后发布；不要直接改数据库发布指针或覆盖历史识别记录。迁移为增量兼容，不执行逆向删表。
